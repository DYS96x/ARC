# Standard

> Every ARC system shall be designed, measured and improved according to defined quality expectations.

Quality is not the absence of failure.

Quality is the ability of a system to reliably create intended outcomes while adapting to reality.

---

# Purpose

Define how ARC evaluates and improves the quality of systems, objects, relationships, knowledge and operations.

Quality ensures:

- Reliability
- Maintainability
- Clarity
- Trust
- Continuous improvement

# Quality Principles

## Q001 — Purpose Alignment

A system is only high quality if it solves the correct problem.

Quality begins with understanding reality.

---

## Q002 — Correctness

Systems should produce expected outcomes according to defined requirements and responsibilities.

Correctness requires:

- Clear expectations
- Validation
- Testing
- Evidence

---

## Q003 — Reliability

Systems should behave consistently under expected conditions.

Reliability includes:

- Stability
- Predictability
- Recovery
- Error handling

---

## Q004 — Simplicity

Systems should minimise unnecessary complexity.

Complexity should only exist where it creates meaningful capability.

---

## Q005 — Maintainability

Systems should be understandable and changeable.

Maintainability requires:

- Clear design
- Documentation
- Separation of concerns
- Testability

---

## Q006 — Observability

Systems should make their condition visible.

Quality requires understanding:

- What happened
- Why it happened
- What changed
- What needs improvement

---

## Q007 — Performance

Systems should use resources responsibly.

Performance evaluation should consider:

- User experience
- Efficiency
- Scalability
- Cost
- Sustainability

---

## Q008 — Resilience

Systems should handle expected failure.

Resilience includes:

- Detection
- Recovery
- Degradation handling
- Learning from failure

---

## Q009 — Continuous Improvement

Every system should improve through:

```text
Measure

↓

Learn

↓

Change

↓

Validate

↓

Improve
```

---

## Q010 — Quality Evidence

Quality claims require evidence.

Evidence may include:

- Tests
- Metrics
- Reviews
- User outcomes
- Operational data
- Audits

---

# Quality Assessment

Every major capability should evaluate:

## Function

Does it achieve its purpose?

## Reliability

Can it be trusted?

## Security

Can it operate safely?

## Maintainability

Can it evolve?

## Experience

Does it reduce friction?

## Learning

Does it improve future capability?

---

# Quality Gates

Before release or approval:

A capability should demonstrate:

- Defined purpose
- Verified responsibility
- Tested behaviour
- Known limitations
- Evidence of performance
- Documented risks

---

# Quality Violations

The following violate this standard:

- Building without purpose.
- Measuring without evidence.
- Ignoring known failures.
- Creating unnecessary complexity.
- Releasing without validation.
- Hiding quality problems.
- Preventing improvement.
